# Rain Bird IQ4 Cloud API Specification

This document details the **Rain Bird IQ4 REST API (Rain Bird 2.0 app)** protocol. Modern Rain Bird controller firmware upgrades migrate devices from the local JSON-RPC / LNK client API to this cloud-based platform.

This specification is based on the custom component implementation by [@davidsuarez82](https://github.com/davidsuarez82) in [davidsuarez82/rainbird_iq4](https://github.com/davidsuarez82/rainbird_iq4).

---

## 1. Authentication Infrastructure

The IQ4 cloud platform uses OAuth 2.0 / OpenID Connect (OIDC) JWT token-based authentication.

- **Authentication Base URL:** `https://iq4server.rainbird.com/coreidentityserver`
- **API Base URL:** `https://iq4server.rainbird.com/coreapi/api`
- **OAuth Client ID:** Any dynamically generated random UUID (e.g., `C5A6F324-3CD3-4B22-9F78-B4835BA55D25`). The official app generates a UUID on initial setup using `UUID.randomUUID().toString()` and stores it as the `APP_CLIENT_ID` in preferences.
- **Redirect URI:** `https://iq4.rainbird.com/auth.html`

### Authentication Standards & Reference Documents

The headless authentication flow implements standard Microsoft server security patterns. For architectural validation, refer to:
* **OIDC Implicit Flow Protocol**: The identity server exposes standard OpenID Connect endpoints. See [Microsoft OAuth 2.0 Implicit Flow Specification](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-implicit-grant-flow).
* **ASP.NET Core Identity Authentication**: The form-based login uses the default identity engine. See [ASP.NET Core Identity Documentation](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity).
* **Antiforgery (CSRF) Security**: The `__RequestVerificationToken` parameter is generated by ASP.NET's built-in Cross-Site Request Forgery mitigation. Echoing it is a strict requirement of the Microsoft security middleware. See [ASP.NET Core Antiforgery Spec](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery).

### Authentication Flow (Browser Emulation / Bypass)

AWS WAF protects the authentication endpoints, typically requiring clients to handle cookies and headers properly (e.g., using `curl_cffi` to impersonate browser fingerprints).

1. **Initiate Authorization Request:**
   Generate a random hexadecimal `state` and `nonce` (8 bytes each). Build the Return URL:
   ```
   /coreidentityserver/connect/authorize/callback?client_id=C5A6F324-3CD3-4B22-9F78-B4835BA55D25&redirect_uri=https%3A%2F%2Fiq4.rainbird.com%2Fauth.html&response_type=id_token%20token&scope=coreAPI.read%20coreAPI.write%20openid%20profile&state=<STATE>&nonce=<NONCE>
   ```

2. **Retrieve Login Page & CSRF Token:**
   Perform a GET request to:
   ```
   https://iq4server.rainbird.com/coreidentityserver/Account/Login?ReturnUrl=<URL_ENCODED_RETURN_URL>
   ```
   Extract the verification token value from the HTML response:
   ```html
   <input name="__RequestVerificationToken" type="hidden" value="<CSRF_TOKEN>" />
   ```

3. **Submit Credentials:**
   Perform a POST request to the same Login URL with the following form-encoded payload:
   - `Username`: `<User Email>`
   - `Password`: `<User Password>`
   - `ReturnUrl`: `<UNENCODED_RETURN_URL>`
   - `__RequestVerificationToken`: `<CSRF_TOKEN>`

4. **Follow the Redirect Chain & Extract JWT:**
   The credential POST must be sent **without auto-following redirects**
   (`allow_redirects=false`). A successful login returns a `301/302` whose
   `Location` header typically points back to the OIDC
   `connect/authorize/callback` endpoint — **not** directly to the redirect URI.
   Follow the chain of `30x` redirects **manually** (carrying cookies forward)
   until a `Location` starts with the redirect URI (`https://iq4.rainbird.com/auth.html`).
   Its **hash fragment** carries the tokens:
   ```
   https://iq4.rainbird.com/auth.html#id_token=<JWT>&access_token=<JWT_ACCESS_TOKEN>&token_type=Bearer&expires_in=3600&state=<STATE>&session_state=<SESSION_STATE>
   ```
   Parse the fragment to extract `access_token` (and `expires_in`, ~3600s).

   > **Note on `client_id`:** the doc's random-UUID approach works, but the
   > reference implementation uses a single fixed UUID
   > (`C5A6F324-3CD3-4B22-9F78-B4835BA55D25`). Either is accepted; whichever you
   > pick should stay **stable** across logins for a given install.

   > **Note on WAF:** if the login page (or a `200` response to the POST) contains
   > a CAPTCHA / WAF challenge, back off and retry. A native (non-browser) TLS
   > fingerprint may be blocked with `403`.

5. **API Header Authorization:**
   Add the retrieved access token to all subsequent API requests:
   ```http
   Authorization: Bearer <JWT_ACCESS_TOKEN>
   Accept: application/json
   ```

## 2. API Endpoints Reference

All API calls are relative to the API Base URL: `https://iq4server.rainbird.com/coreapi/api/`.

### 2.1 Satellites (Controllers)

#### List Satellites (Discovery)
- **HTTP Method:** `GET`
- **Path:** `Satellite/GetSatelliteList`
- **Query Parameters:**
  - `includeInvisibleToCurrentUser`: `false`
- **Description:** Returns **all controllers registered on the account**. This is
  the discovery endpoint used to obtain the numeric `id` (the `satelliteId`)
  required by every other call. Response is a JSON array of satellite objects,
  each with at least `id` and `name`.

#### Get Satellite Details
- **HTTP Method:** `GET`
- **Path:** `Satellite/GetSatellite`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns the details of a specific controller (includes
  `siteId`, `rainDelayLong`, forecast fields, etc.).

#### Get Connection Status
- **HTTP Method:** `GET`
- **Path:** `Satellite/isConnected`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns whether the controller is actively connected to the
  cloud service. Response is an object of the form `{ "satellites": [<ID>, ...] }`
  listing the connected satellite IDs.

#### Stop All Irrigation
- **HTTP Method:** `POST`
- **Path:** `Satellite/StopAllIrrigation`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:** `[<SATELLITE_ID>]`
- **Description:** Immediately stops all active irrigation on the controller.

#### Get Firmware Versions
- **HTTP Method:** `GET`
- **Path:** `ManualOps/GetSatelliteFirmwareVersions`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns firmware and modular-system version information.

#### Update Satellite Configuration (Rain Delay / Forecast)
- **HTTP Method:** `PATCH`
- **Path:** `Satellite/v2/UpdateBatches`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:**
  ```json
  {
    "ids": [<SATELLITE_ID>],
    "patch": [
      { "op": "replace", "path": "/<FIELD>", "value": <VALUE> }
    ]
  }
  ```
- **Common Fields to Patch:**
  - `/rainDelayLong`: Rain delay duration in .NET ticks (1 tick = 100ns; e.g. `days * 24 * 3600 * 10,000,000`).
  - `/rainDelayStart`: ISO-8601 UTC timestamp of delay start (e.g., `2026-06-13T17:20:00Z`).
  - `/useForecast`: Boolean to enable/disable forecast-based rain delay.
  - `/forecastPercentLimit`: Integer rain probability threshold (0-100).
  - `/forecastInchesLimit`: Float precipitation depth threshold (in inches).
  - `/forecastDelayDays`: Integer delay days.

### 2.2 Programs

#### Get Program List
- **HTTP Method:** `GET`
- **Path:** `Program/GetProgramList`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns all irrigation programs (e.g., A, B, C, D) configured on the satellite.

#### Update Program Configuration (Seasonal Adjust)
- **HTTP Method:** `PATCH`
- **Path:** `Program/UpdateBatches`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:**
  ```json
  {
    "ids": [<PROGRAM_ID>],
    "patch": [
      { "op": "replace", "path": "/<FIELD>", "value": <VALUE> }
    ]
  }
  ```
- **Common Fields to Patch:**
  - `/etAdjustType`: Weather adjust method integer (e.g., `6` for manual, `7` for automatic seasonal adjust).
  - `/programAdjust`: Seasonal adjustment percentage integer (e.g., `5` to `200` percent).

### 2.3 Stations (Zones)

#### Get Station List
- **HTTP Method:** `GET`
- **Path:** `Station/GetStationListForSatellite`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns metadata for all stations/zones attached to the controller.

#### Get Station Run Status
- **HTTP Method:** `GET`
- **Path:** `ProgramStep/GetRunStationStatusForSatellite`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns real-time execution status for all zones (e.g., running, idle, paused).

#### Get Programs Assigned Runtime
- **HTTP Method:** `GET`
- **Path:** `ProgramStep/GetProgramsAssignedAndRunTimeBySatelliteId`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Returns configured runtimes per station mapped to programs.

### 2.4 Manual Operations

#### Start Station Manually
- **HTTP Method:** `POST`
- **Path:** `ManualOps/StartStations`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:**
  ```json
  {
    "stationIds": [<STATION_ID>],
    "seconds": [<RUN_DURATION_SECONDS>],
    "isGroupStart": false
  }
  ```

#### Stop / Advance Station
- **HTTP Method:** `POST`
- **Path:** `ManualOps/AdvanceStations`
- **Query Parameters:**
  - `isProgramIndex`: `true`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:**
  ```json
  [
    {
      "programId": -1,
      "stationId": <STATION_ID>
    }
  ]
  ```

#### Start Programs Manually
- **HTTP Method:** `POST`
- **Path:** `ManualOps/StartPrograms`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:** `[<PROGRAM_ID>, ...]`
- **Description:** Triggers execution of one or more programs by their numeric ID.

### 2.5 Sensors & Flow Elements

#### Get Sensor List
- **HTTP Method:** `GET`
- **Path:** `Sensor/GetSensorListBySatelliteId`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Description:** Lists rain, wind, or soil sensors hooked to the controller.

#### Get Flow Zones/Elements
- **HTTP Method:** `GET`
- **Path:** `FlowElement/GetFlowElements`
- **Query Parameters:**
  - `satelliteId` (integer)
- **Note:** The reference client passes only `satelliteId`. Some clients
  additionally send `parentId` (empty string) and `includeHiddenFlowZones=false`;
  both are optional and default to the root/visible flow zones.

#### Get Seasonal Adjust
- **HTTP Method:** `GET`
- **Path:** `SeasonalAdjust/GetSeasonalAdjustForSite`
- **Query Parameters:**
  - `siteId` (integer) — obtained from `Satellite/GetSatellite` (`siteId` field),
    **not** the satelliteId.
- **Description:** Returns the seasonal watering adjust configuration for the site.

#### Get Flow Monitoring Config
- **HTTP Method:** `GET`
- **Path:** `FlowMonitoring/GetFlowMonitoringBySatelliteId`
- **Query Parameters:**
  - `satelliteId` (integer)

---

### 2.6 System Logs & Alerts

#### Get Company Status (Alerts Summary)
- **HTTP Method:** `GET`
- **Path:** `Company/GetCompanyStatusCore`
- **Query Parameters:**
  - `companyId` (integer)
- **Description:** Retrieves high-level warning and alarm counts for the user account's parent company.

#### Get Event Logs
- **HTTP Method:** `POST`
- **Path:** `EventLog/GetEventLogsBySatelliteIds_V2`
- **Query Parameters:**
  - `startTime` (string: `YYYY-MM-DDTHH:MM:SS`)
  - `endTime` (string: `YYYY-MM-DDTHH:MM:SS`)
  - `types`: `15`
  - `includeAcknowledgedAlarms`: `true`
  - `includeAcknowledgedWarnings`: `true`
- **Headers:** `Content-Type: application/json`
- **JSON Request Body:**
  ```json
  [<SATELLITE_ID>]
  ```
- **Known Event Identifiers (`eventParameter1` contains station terminal index):**
  - `97`: Station turned on.
  - `98`: Station turned off.
  - `15000`: Irrigation run completed.
  - `15001`: Automatic seasonal adjust changed.
  - `15002`: Rain delay enabled.
  - `15011`: Rain delay expired/disabled.

## 3. Node-RED Nodes (this package)

This package implements the IQ4 cloud API as an **alternative transport** to the
local LNK2/SIP nodes. It is aimed primarily at data the local protocol does not
expose (flow monitoring, full program configuration). All cloud nodes are pure
Node core (`https`) — **no external dependencies**.

### 3.1 Nodes

| Node | Purpose |
|------|---------|
| `rainbird-iq4-server` (config) | Stores account credentials, Satellite ID, and a stable `APP_CLIENT_ID`. Owns a single shared client (one login/token reused by all nodes). |
| `rainbird-iq4-satellites` | Discovery: lists all controllers on the account so you can find the numeric `satelliteId`. |
| `rainbird-iq4-flow` | Reads flow elements (and, where available, flow monitoring). |
| `rainbird-iq4-programs` | Reads the program list and per-station assigned runtimes. |

### 3.2 First-time setup

1. Add any cloud node and, in its **Server** field, create a
   `rainbird-iq4-server` config node with your **email** / **password**.
   (`Satellite ID` may be left empty for the discovery step.)
2. Trigger a `rainbird-iq4-satellites` node — `msg.payload` is the array of
   controllers. Copy the `id` of your controller into the config node's
   **Satellite ID**.
3. Use `rainbird-iq4-flow` / `rainbird-iq4-programs`. `msg.satelliteId` overrides
   the config node's Satellite ID per message.

### 3.3 Authorization behaviour

- OIDC implicit flow → access token only (~1h), **no refresh token**. The client
  caches the token and re-logs in automatically on expiry (60s safety margin) or
  on a `401` (one forced re-login + retry per request).
- A **mutex** ensures concurrent nodes share a single in-flight login (so they
  don't hammer the WAF).
- WAF `403` / CAPTCHA challenges are detected and surfaced as explicit errors.

### 3.4 Debugging

Enable **Debug** on the `rainbird-iq4-server` config node to log the full auth
flow to the Node-RED log (safe — secrets are masked, tokens shown as
`<len=…last6>`, redirect URLs logged without query params). Typical trace:

```
IQ4: login start: user=you@example.com clientId=<UUID>
IQ4: GET login page: HTTP 200, 12345 bytes, cookies=[.AspNetCore.Antiforgery.xxxx]
IQ4: CSRF token extracted (88 chars)
IQ4: POST credentials: HTTP 302, location=yes
IQ4: redirect hop 0: GET https://iq4server.rainbird.com/coreidentityserver/connect/authorize/callback
IQ4: redirect hop 1: reached redirect URI
IQ4: authenticated: token=<len=1234…AbCdEf>, valid for ~3600s
IQ4: GET Satellite/GetSatelliteList -> HTTP 200
```

Common failure signatures:
- `blocked by AWS WAF (HTTP 202)` → **AWS WAF JavaScript challenge** (body
  contains `window.awsWafCookie…`). This is the common blocker: the WAF serves a
  JS proof-of-work page that sets an `aws-waf-token` cookie. A plain HTTP client
  (Node **or** Python/aiohttp) cannot solve it — it requires executing the
  challenge JavaScript in a browser, or presenting a real browser TLS fingerprint
  (e.g. `curl_cffi`) so the WAF doesn't challenge at all. The client retries 3×
  with backoff (10/20/30s) in case the challenge is transient, then fails.
  **Workaround:** use the manual **Access token** (see below).
- `authentication failed (check email/password)` → POST re-rendered the login
  page (bad credentials).
- `could not extract __RequestVerificationToken` → login page markup changed.
- `Cannot find module '…'` on load → a dependency isn't resolvable; the cloud
  nodes intentionally avoid external deps to prevent this.

### 3.5 Manual access token (AWS WAF bypass)

Because headless login is blocked by the WAF JS challenge, the config node accepts
an optional **Access token**. When set, the login flow is skipped and the token is
used directly for API calls.

To obtain it: log in at `https://iq4.rainbird.com` in a browser, open DevTools →
Network, pick any `coreapi` request, and copy the value after
`Authorization: Bearer`. Paste it into the config node.

The token is a standard OIDC access token valid ~1 hour, so it must be refreshed
manually. This mode also serves as a diagnostic: if API calls succeed with a
browser token, the `coreapi` tier itself is reachable from Node and only the
login endpoints are WAF-gated.

**AWS WAF token cookie (fuller automation):** the challenge is satisfied by an
`aws-waf-token` cookie that the browser's challenge JS sets. Copy it from
DevTools → Application → Cookies → `iq4server.rainbird.com` and paste it into the
config node's **AWS WAF token** field. It is injected into every request, so the
*automated* login (and API calls) can pass the WAF and the client refreshes the
JWT itself. This is more general than the manual access token (it also unblocks a
WAF-gated `coreapi`), but only for the duration of the token's "immunity time",
which Rain Bird configures and may be short.

> **Confirmed:** the reference `pyrainbird` client (plain `aiohttp`) is blocked by
> the same `HTTP 202` WAF challenge. Headless login is not solvable by any plain
> HTTP client; a real browser TLS fingerprint (`curl_cffi`) or a browser-obtained
> token/cookie is required.
